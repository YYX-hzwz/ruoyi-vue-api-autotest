# 从 0 到这个项目：21 天学习路线

> 写给"项目是别人帮我重构的、我要在一个月内真正吃透它"的你。
> 原则：**先能跑，再能改，最后能讲**。不要从第一行代码开始顺序读——那是效率最低的方式。

---

## 先建立一个心理预期

这个项目**故意不炫技**：没有 Allure、没有 pydantic、没有 Kubernetes。
它炫的是另外三样东西，而这三样恰好是面试官真正会追问的：

1. **边界感**：哪一层该放断言、哪一层不该；
2. **诚实度**：发现了缺陷，是写成红色用例，还是写成 `assert 200`；
3. **可诊断性**：用例挂了，你能不能在三分钟内说清为什么挂。

所以学习重点不是"记住 148 条用例"，而是"能解释 10 个设计决策"。
下面第 5 节的 10 个问题，就是验收标准。

## 第 0 天：先跑起来（30 分钟）

```powershell
cd C:\Users\HP\RuoYi-Vue\autotest
copy .env.example .env
py -m pytest -q
```

你会看到：`144 passed, 3 xfailed, 1 skipped`。

**然后做这一件事**：打开 `reports/report.html`，随便点开一条失败的（xfail）用例，
看它的「API 交互记录」附件。你要能回答：这条用例发了什么请求、收到什么响应、
为什么判定它失败。

再看一眼 `reports/QUALITY.md`。这就是你以后在面试里"展示作品"时打开的第一个文件。

## 第 1 周：读懂框架（每天 1~2 小时）

顺序很重要：**从下往上读**，因为上层依赖下层。

### Day 1 — 配置与 HTTP（`framework/settings.py`、`framework/http.py`）

读之前先回答：如果一个接口自动化项目没有设置 timeout，最坏会发生什么？

读完要能说出：
- 为什么 `Settings` 是 `frozen`（不可变）？
- `http.py` 顶部的注释列了 4 个坑，分别对应哪几行代码？
- 为什么 POST 默认不重试？

动手：把 `AUTOTEST_HTTP_READ_TIMEOUT` 改成 `0.001`，跑一条用例，看错误长什么样。
改回来。

### Day 2 — 断言与契约（`framework/assertions.py`、`framework/schema.py`）

这是全项目最值钱的两个文件。

读完要能说出：
- `expect_ok` 和 `assert resp.json()["code"] == 200` 的差别，具体在哪一行体现？
- `expect_perm_denied` 为什么断言 `code == 403` 而不是 `status_code == 403`？
- `validate()` 为什么返回"全部错误"而不是遇到第一个就抛？
- 为什么默认允许后端新增字段？

动手：把 `ruoyi/schemas.py` 里 `USER_ROW` 的 `"userId": S.int(ge=1)` 改成 `S.str()`，
跑一条用例，看报错信息能不能精准指出是哪一行、哪个字段。

### Day 3 — 追踪与装配（`framework/trace.py`、`conftest.py`）

这一天读 `conftest.py` 会有点吃力，不要慌，抓三条主线：

1. **装备线**：`base_url` → `admin_http`（创建即登录）→ `admin_auth` / `user_api` / `role_api` / `system_api`
2. **数据线**：`user_factory` → 创建 → 查 id → 用例 → teardown 清理
3. **观测线**：`_api_trace`（开始清空）→ `RECORDER`（记录）→ `pytest_runtest_makereport`（挂附件）

读完要能说出：为什么登录要写在 `admin_http` 里，而不是让 `user_api` 去依赖一个"负责登录"的 fixture？
（提示：我第一版就是那种依赖链——全量跑没问题，但单独跑 `pytest -m contract` 时没有任何用例
触发登录，整个会话 401。这种隐藏耦合只有跑子集时才暴露，也是"为什么每个 fixture 都要能独立成立"的实例。）

### Day 4 — 领域层（`ruoyi/`）

重点看三个"约定"：

- `ruoyi/base.py` 顶部注释：**API 层不做断言**，为什么？
- `ruoyi/user.py` 的 `assign_roles`：为什么用 query 参数而不是 JSON body？
- `ruoyi/factories.py`：`user_payload()` 为什么要生成唯一值，而不是用固定值？

### Day 5 — 用例（`tests/`）

按 `test_01 → 02 → 03 → 05 → 07 → 08 → 09` 的顺序读。
`test_04` 和 `test_06` 是 CRUD 的重复套路，可以快读。

重点回答：
- `test_02_user_crud.py::test_user_list_pagination_is_effective` 为什么要同时看 `total`？
  （提示：`len(rows) <= pageSize` 是假断言）
- `test_05_permission_matrix.py` 的矩阵为什么要把"删除用户"写成 `delete(999_999)`？
- `test_09_meta.py` 在守护什么？举出它拦得住的两个坏味道。

## 第 2 周：读懂"为什么这么设计"

这一周不读代码，只读 `docs/`。

| 天 | 读什么 | 要能回答 |
|----|--------|----------|
| 1 | `docs/defects.md` | BUG-002 的假设-验证表怎么用？为什么不能直接定性为"越权"？ |
| 2 | `docs/defects.md` 的"认知修正" | 验证码那个"缺陷"为什么其实不是缺陷？原来错在哪？ |
| 3 | `docs/architecture.md` | 加一个新接口要改 5 个文件，分别是哪 5 个？为什么不用改 framework？ |
| 4 | `docs/test_plan.md` | 五层策略各解决什么问题？准入准出标准是什么？ |
| 5 | `README.md` 第 10 节 | 哪些验证过、哪些没验证过？为什么要在 README 里写这个？ |

第 5 天结束时，你应该能对着空白纸画出来：

```
tests → ruoyi → framework
         ↓
      stub / real backend
```

## 第 3 周：动手（三个练习，由易到难）

### 练习 1（半天）：加一套"岗位管理"的 CRUD

按 `docs/architecture.md` 第 4 节的 5 步做：

1. `ruoyi/system.py` 加 `post_create/post_update/post_delete`
2. `ruoyi/schemas.py` 加 `POST_ROW/POST_PAGE`
3. `ruoyi/factories.py` 加 `post_payload()`
4. `conftest.py` 加 `post_factory`
5. `tests/test_10_post_crud.py` 写 6 条用例

**验收**：`py -m pytest -q` 全绿，且 `test_09_meta.py` 不报错（说明你没有引入硬编码/裸 sleep）。

这一步做完，你就真正理解分层了。

### 练习 2（半天）：自己发现并固化一个缺陷

1. 在 `stub/app.py` 里故意埋一个 bug（比如"修改用户时不校验邮箱唯一性"）
2. 在 `defects/registry.json` 加一条记录
3. 写一条 `@pytest.mark.defect("BUG-004") + @pytest.mark.xfail` 的用例
4. 跑两次：`AUTOTEST_STUB_REPRODUCE_BUGS=true` 应 xfail，`=false` 应 xpass

**验收**：`test_09_meta.py` 通过（它会检查缺陷与用例是否双向绑定）。

这一步做完，你就掌握了"缺陷 → 用例 → 修复 → 回归"的完整闭环——
这是面试里最能讲出深度的一段。

### 练习 3（1~2 天）：接真实后端

按 `docs/run-real-backend.md` 跑通一次。重点观察：

- 真实环境里 3 条缺陷用例的 xfail/xpass 与桩是否一致？
- 如果不一致，是"桩漂移"还是"真实后端行为不同"？
- 分页、唯一约束、权限拦截的文案有没有差异？

**这一步的产物是你简历里最硬的一句话**：
「在 RuoYi-Vue 3.9.2 真实环境跑通 148 条用例，修复 N 处桩与真实后端的契约差异」。

## 面试问答 10 题（附答案要点）

> 建议：每题的答案都去对应文件里找到那几行代码，面试时能说出文件名。

**Q1：介绍一下你这个项目。**
→ 一句话定位（RuoYi 接口自动化框架，148 条用例，5 层策略）+ 一个亮点（3 个缺陷用 xfail 固化）
+ 一个边界（契约桩不是被测系统）。**不要**从"我用 pytest 和 requests"开头。

**Q2：为什么用例数从 43 涨到 148，是堆出来的吗？**
→ 增长来自三处，每处都是"一个函数覆盖一类问题"：权限矩阵 14 项、参数化非法输入 15 组、
契约断言 13 个。代码量反而下降了（fixture 从 6 份重复收敛成 1 份）。
→ 文件：`tests/test_05`、`tests/test_03` + `data/cases/user_validation.json`、`tests/test_07`

**Q3：你发现了什么缺陷？怎么证明的？**
→ 讲 BUG-002 最出彩：现象 → 两个假设（缺注解 / 菜单权限误配）→ 验证方法 →
辅助证据（`/getRouters` 无该菜单，说明两套权限来源不一致）→ 因此"待确认"而不是直接定性。
→ 文件：`docs/defects.md`

**Q4：缺陷为什么是 xfail，不是直接跳过或者改断言？**
→ 跳过 = 放弃回归；改断言 = 把缺陷固化成需求。xfail 保留"红"的信号，修复后自动转 xpass 并提示清理。
→ 文件：`tests/test_08_defects.py` 顶部注释

**Q5：用例失败时你怎么定位？**
→ 报告里有请求/响应 JSON 和 cURL；断言信息带 method/url/HTTP/code/msg/body；
→ 文件：`framework/trace.py`、`conftest.py` 的 `pytest_runtest_makereport`

**Q6：怎么保证用例可以重复跑、并行跑？**
→ 唯一数据（uuid）+ `at_` 前缀 + fixture 清理 + 不碰固定 ID + 按 roleKey 解析角色。
→ 文件：`framework/data.py`、`conftest.py` 的 `user_factory`

**Q7：怎么区分"权限拦截"和"参数校验失败"？**
→ 断言具体 `code=403` + msg 包含"没有权限"；并且用管理员视角回查副作用，
防止"返回 403 但其实写进去了"。
→ 文件：`framework/assertions.py::expect_perm_denied`、`tests/test_05` 的提权用例

**Q8：CI 怎么做的？**
→ 两个 job：桩全量（每次 push）+ 真实后端 e2e（手动触发）；桩 job 跑两轮做缺陷生命周期校验；
→ 产物上传 `reports/`；静态检查用 ruff 的语法级规则。
→ 文件：`.github/workflows/ci.yml`

**Q9：为什么要有契约桩？它会不会掩盖真实问题？**
→ 会，所以边界写死：运行时横幅、README、报告都标注"非被测系统"；
→ 桩解决"CI 里起不起后端"的问题，真实结论由 e2e job 兜底。
→ 文件：`stub/app.py` 顶部注释、`conftest.py::pytest_configure`

**Q10：如果让你继续做，下一步做什么？**
→ 三个方向（选一个讲深）：UI 层（Playwright，API 造数 + UI 断言）、
数据层（Testcontainers / DB 直连精确造数）、质量平台（用例管理 + 调度 + 看板）。
→ 文件：`README.md` 第 12 节、`docs/学习路线.md` 进阶

## 学习陷阱（我见过太多人踩）

1. **从 `conftest.py` 第一行开始顺序读** → 会被 fixture 依赖绕晕。先画依赖图，再读实现。
2. **试图记住所有 API 方法** → 不用。记住"API 层不断言"这一条，其余查文件。
3. **跳过 `docs/`** → 这个项目一半的价值在文档里。代码回答"怎么做"，文档回答"为什么"。
4. **只看不跑** → 每条你要讲的设计，都在本机跑一遍看输出。尤其是失败的样子。
5. **把 148 这个数字当成卖点** → 卖点是"148 条里有 3 条会红"。

## 如果只有 3 天

优先级从高到低：

1. 第 0 天（跑起来 + 看报告）—— 2 小时
2. `framework/assertions.py` + `tests/test_08_defects.py` + `docs/defects.md` —— 半天
3. 面试问答 10 题，每题准备 60 秒口述 —— 一天
4. 练习 1（加岗位 CRUD）—— 半天

这四件事能覆盖面试里 80% 的追问。剩下的（权限矩阵、契约层、docker）等拿到面试再补。
