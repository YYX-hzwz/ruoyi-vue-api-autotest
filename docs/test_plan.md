# 测试方案

## 1. 目标

验证 RuoYi-Vue 后台管理系统**接口层**的功能正确性、输入健壮性、权限隔离与响应契约，
并在缺陷存在时给出**可复现、可持续回归**的失败信号。

明确不追求：UI 交互细节、浏览器兼容性、并发压测的容量结论（后者由 `performance_test/` 单独负责）。

## 2. 范围

| 模块 | 覆盖接口 | 用例数（约） |
|------|----------|--------------|
| 认证 | /login、/logout、/captchaImage、/getInfo、/getRouters | 15 |
| 用户管理 | list、get、create、update、delete、resetPwd、changeStatus、authRole | 35 |
| 角色管理 | list、get、create、update、delete、changeStatus、dataScope | 20 |
| 权限 | 14 项接口 × 普通角色 | 18 |
| 公共数据 | 字典、参数、公告、菜单、部门、岗位 | 14 |
| 契约 | 13 个读接口 + 5 个分页接口的信封一致性 | 13 |
| 缺陷回归 | 3 个已知缺陷 | 3 |

不在范围：文件上传下载、定时任务、代码生成器、WebSocket 通知、多数据源。

## 3. 策略：五层

### 3.1 冒烟层（`test_01_auth.py`）
只回答一个问题：**这套环境还能不能测**。登录拿 token、`/getInfo` 返回身份、`/getRouters` 返回菜单。
这一层红了，后面所有用例都没有意义，应该先修环境再看结果。

### 3.2 功能层（`test_02`、`test_04`、`test_06`）
CRUD 的正确性，核心方法是**写后回查**：

```
创建 → 用返回值查详情 → 字段逐一比对
更新 → 重新 get → 断言字段真的变了
删除 → 再查 → 断言 404/业务错误
```

只断言 `code == 200` 无法发现"返回成功但事务回滚了""异步没落库"这类缺陷。

### 3.3 校验层（`test_03`）
- 等价类：合法 / 非法用户名、邮箱、手机号
- 边界值：30/31 字符、50/51 字符、11/12 位手机号
- 特殊字符：SQL 注入串、XSS 串、LIKE 通配符、emoji
- 数据驱动：非法用例写在 `data/cases/user_validation.json`，加一条不用改代码

### 3.4 权限层（`test_05`）
用**普通角色账号**横向扫一遍受控接口，形成 14 项矩阵。三个原则：

1. **区分 401 与 403**：未认证是 401，已认证无权限是 403。混为一谈会掩盖 token 失效。
2. **区分根因**：403 必须带"没有权限"文案，不能是"参数校验失败恰好也 403"。
3. **不碰真实数据**：删除类越权用不存在的主键；验证"没被篡改"用管理员视角回查。

### 3.5 契约层（`test_07`）
不关心业务值，只关心接口"说话算不算数"：Content-Type、`code` 类型、分页信封一致性、
错误信封一致性、中文编码。这一层最适合在 CI 里快速回归——它最先红、定位最便宜。

## 4. 数据策略

| 问题 | 做法 |
|------|------|
| 唯一索引冲突 | `uuid4` 生成 userName/phone/email，任意次重跑不撞 |
| 数据污染 | 所有生成值带 `at_` 前缀；fixture teardown 自动清理；负向用例另有兜底清理 |
| 主键硬编码 | 角色按 `roleKey` 解析（`common_role_id` fixture），不写 `roleIds=[2]` |
| 环境相关值 | deptId/postId 等来自 `ruoyi/constants.py`，集中管理，换环境只改一处 |
| 造数方式 | 优先走 API（黑盒）；对"必须存在但接口建不出来"的数据，才考虑 DB 直连 |

## 5. 环境

| 环境 | 用途 | 启动方式 |
|------|------|----------|
| 契约桩 | 本地开发、CI 快速回归、缺陷演示 | 内置，`pytest` 自动在随机端口启动 |
| 本地真实后端 | 验收、缺陷复现、性能基线 | `scripts/run-real.ps1` / docker compose |

## 6. 准入与准出

**准入**
- 后端可访问且 `/captchaImage` 返回 200
- 管理员账号可登录（验证码已关闭，或框架能取到验证码）
- `common` 角色存在（权限矩阵依赖）

**准出**
- 冒烟层 100% 通过
- 功能/校验/权限/契约层通过率 100%
- 已知缺陷：xfail 数量与 `defects/registry.json` 中 `status=open` 的数量一致
- 无新增 `skipped`（除环境性跳过，需在报告里注明原因）

## 7. 度量

| 指标 | 口径 | 目标 |
|------|------|------|
| 用例通过率 | passed / (total - skipped - xfailed) | 100% |
| 缺陷回归覆盖 | 有绑定用例的 open 缺陷 / open 缺陷 | 100%（meta test 保证） |
| 执行时长 | 全量 | 桩 < 10s，真实后端 < 60s |
| 失败可诊断率 | 带请求响应附件的失败用例 / 失败用例 | 100% |
| 脚本稳定性 | 连续 3 次全量无 flaky | 100% |

## 8. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 用例互相污染（共享真实库） | 偶发失败，难以复现 | 唯一数据 + fixture 清理 + 不碰固定 ID |
| 后端版本漂移导致契约变化 | 大批用例变红，误判为回归 | 契约层单独 marker，先跑 `-m contract` 定位 |
| 权限配置差异（菜单权限 vs 注解） | 越权用例"错误理由通过" | 断言具体 msg + 用管理员视角验证副作用 |
| 长事务/主从延迟 | 写后回查偶发查不到 | `eventually` 轮询而非 `sleep` |
| 验证码策略变化 | 登录失败，全量阻塞 | 三条取码路径（固定码/Redis/桩）+ 明确报错 |
