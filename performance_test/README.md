# 性能测试

## 跑之前

需要一个可访问的 RuoYi 后端（真实或契约桩均可，但**基线数字必须来自真实后端**）。

```bash
pip install locust
locust -f performance_test/locustfile.py --headless -t 3m --html reports/perf.html
```

默认连 `http://localhost:8080`，账号 `admin/admin123`。

## 参数

| 环境变量 | 默认 | 说明 |
|----------|------|------|
| `LOCUST_HOST` | `http://localhost:8080` | 被测地址 |
| `LOCUST_USER` / `LOCUST_PASS` | `admin` / `admin123` | 登录账号 |
| `SLA_P95_MS` | `800` | P95 上限，超了进程退出码 = 1 |
| `SLA_FAIL_RATIO` | `0.01` | 失败率上限 |
| `LOCUST_SHAPE` | `1` | `0` 关闭阶梯加压，改用 `-u/-r` |

权重按"后台真实流量分布"估算，不是平均分配。压测前应先用访问日志校准。

## 为什么必须做业务断言

RuoYi 的错误响应是 `HTTP 200 + body.code=500`。如果只看 HTTP 状态码：

- 数据库连接池打满 → 业务码 500 → 算成功
- 权限异常 → 业务码 403 → 算成功
- 接口超时被网关包装 → 可能仍是 200

所以 `locustfile.py` 里的 `_get()` 用 `catch_response=True` 并校验 `body["code"] == 200`，
失败会进 `fail_ratio`，进而触发 SLA 门禁。

## 怎么解读结果

关注四件事，按顺序：

1. **TPS 拐点**：并发从 30 加到 60，TPS 是否还在涨？不涨就是瓶颈到了。
2. **P95 随并发的劣化曲线**：线性上升 = 资源不足；突然阶跃 = 连接池/锁/GC。
3. **失败率**：先看是 5xx 还是业务码失败。业务码失败往往比 5xx 更早出现。
4. **RPS 最高的那个接口**：通常就是瓶颈所在（本项目预期是用户列表）。

RuoYi 的常见瓶颈点（按出现频率）：

| 现象 | 可能原因 |
|------|----------|
| 并发 > 20 后 P95 阶跃上升，日志有 `wait millis` | Druid `maxActive` 默认 20 被打满 |
| Redis 相关接口偶发超时 | Lettuce 连接数或超时配置 |
| TPS 上不去但 CPU 不高 | 登录 token 校验走了数据库 / 慢 SQL |
| 长时间压测后内存持续上涨 | 分页查询一次拉全量、导出类接口 |
